Overview

总览

Platform Thinking

客户定义方向与标准，Eastlink 负责开发与执行落地

客户从做执行细节，变成只做关键决策：方向 → 标准 → 确认。客户提交 Brief → 拆解成需求包 → 先设计并定稿（客户唯一确认节点）→ 按维度匹配打样候选 → 候选打样比样 → 内审定商（结果同步客户）→ 合作。所有需要人做判断的动作统一进右侧审核中心；所有资源沉淀在客户、供应商、项目三份主数据里。

Why This Platform

现状六个卡点 → 平台怎么接

① 设计稿不可直接投产AI 稿 / 文字错误 / 结构与实际产品不符，供应商反复检查修改。设计协同：逐 SKU 出稿 + 内审校验
② 设计与规格对不上设计、尺寸、材质信息不一致，来回澄清。标准 PSF：规格书由平台生成，客户只确认
③ 测试要求来得太晚样品出来后才明确测试要求，后期改规格造成返工。PPA 前置：质量要求随设计定稿同步定义
④ 色样多轮返工不同供应商、色样、材料间缺统一标准，重复打样。材料与色彩资产库：Pantone 色卡 + ΔE 验收口径
⑤ 意见多但难落地Comment 很细但缺产品与生产端经验，且不同人意见不一致。审核中心：意见留痕 · 单一决策流
⑥ 人员变动知识断层新人加入 / 休假 / 离职后，项目知识与判断标准无法延续。组织知识库：标准与档案沉淀，不依赖个人

问题不在于投入不够，而在于太多执行性工作压在客户侧——而设计、规格、测试、打样恰恰需要大量产品 / 材料 / 工艺 / 制造知识，这正是平台方最擅长的。Right Work, Right Team.

From Creating To Approving

从"客户执行" 到 "客户确认"

现在

客户：出设计稿 → 写规格 → 定质量与测试要求 → 逐轮提意见 → 给包装信息

平台方：执行 → 打样 → 修改 → 再执行

未来（本 Demo 实现）

客户：方向 → 标准 → 确认

Eastlink：开发 → 规格（PSF）→ 质量前置（PPA）→ 结构验证 → 打样比样 → 优化交付

Stage 1Brief → 设计拆包 + SKU 开发清单 + 逐 SKU 出稿
Stage 2规格 + 质量前置PSF 规格书 + PPA 测试要求，与定稿同步完成
Stage 3打样 → 比价 → 定商门槛匹配 + 按 SKU 评分比样
Stage 4交付与包装验货放行 · 包装刀线（P2）

故事线：客户想更快 → 现有环节返工太多 → 卡点在哪我们清楚 → 把产品专业能力前移 → 客户定方向 → 平台担执行 → 工具与知识库支撑每个项目 → 更少工作 · 更少返工 · 更快交付。

Knowledge System

个人知识 → 组织知识

品牌智能档案材料与色彩资产库 合规验厂标准PSF / PPA 标准模板 SKU 结构沉淀（刀线库 P2）审核与流转全程留痕

项目知识和判断标准沉淀在平台而不是某个人身上——人员变动不再带走项目知识，新人接手即有完整上下文。

需求包状态机设计中 → 待选打样候选 → 打样名单内审 → 打样中 → 定商建议内审 → 已确认合作（结果同步客户）；设计定稿自动进入匹配，内审可退回比样 / 换选（记录原因）。需求包内拆到 SKU，设计与打样都细化到 SKU 跟踪；测试与质量要求（PPA）在设计定稿阶段即定义，新结构 SKU 先出结构样验证再全开发。
客户只做三件事提出 Brief 需求、确认设计稿定稿（唯一确认节点）、提供品牌规范细则（视觉 / 材料色彩 / 合规标准）——定商由 Eastlink 依据打样比样内部确定并同步结果，客户无需二次确认。设计版本内逐 SKU 跟踪出稿覆盖，全出稿才可提交内审。
打样比样候选各自出样，质量 / 工艺还原 / 报价按 SKU 逐项评分，综合分为各 SKU 均值；全部评分后按综合分生成定商建议，单 SKU 异常透明可见，依据全程留痕。
质量控制塔TCF 按 SKU 建档（设计定稿 / 材料声明 / 测试报告 / 样品记录 / 验货报告）；验厂到期预警、测试与验货结果、CAP 整改在塔内闭环——客户合规标准是口径，红线在匹配拦截，塔内跟踪执行；四项就绪门全绿才可进入大货下单（P2）。

Matching Model

匹配模型：硬性门槛 + 加权排序两层

硬性门槛档位说明
准入状态固定硬性必须"已准入 / 合作中"，否则不进入候选
品类覆盖固定硬性主营或兼营须覆盖需求品类
工艺全覆盖固定硬性缺任一需求工艺即排除——做不了就是做不了，不存在"工艺 60 分"
认证全齐可切换（默认评分）打样期间可补办认证；对严格需求可一键切为硬性排除
客户验厂红线可切换（默认警示）打样可并行补审、下单前须完成；可切为硬性排除。正式版按需求包字段级配置
加权排序维度（8 维）默认权重数据来源计算口径
品类专精20主营 / 兼营品类主营 100，兼营 82
认证覆盖17资质证书需求认证覆盖率，缺项列入风险提示
质量表现15质量通过率直接取值
交付可靠12准时率 + 平均交期准时率 60% + 交期达标 40%
价格竞争力12报价竞争力指数直接取值
产能匹配9月产能 vs 需求量富余 1.5 倍满分，不足按比例扣
客户经验8服务过的客户服务过该客户 100 / 有出口经验 65 / 无 40
风险等级7风险评级低 100 / 中 60 / 高 25
为什么分两层工艺这类是"能不能做"的问题，属于门槛；质量价格交期是"谁做得更好"的问题，属于排序。混在一起打分会把"做不了"的供应商排进名单。
门槛开关认证与验厂红线支持现场切换硬性/评分档位，候选实时掉入漏斗排除名单——访谈时直接演示两种口径的差别。
输出漏斗全程透明（每一步排除了谁、为什么）+ 总分 + 维度得分条 + 推荐理由与风险提示；最终由人勾选，系统记录依据。

Roles

角色权限矩阵

业务员管理层客户供应商
总览全量 + 待办全量 + 风险仅自己项目与待确认仅自己的合作
项目管理可操作只读仅自己项目，只读不可见
匹配工作台核心操作不开放不可见不可见
供应商管理全池全池只读"我提供的"全量 + "合作中的"，无内部评分仅自己档案
客户管理可操作只读不可见不可见
审核中心内审动作（含定商确认）查看仅设计稿定稿 / 修改意见打样任务 / 合作通知

原则：客户看不到供应商池全貌、内部打分与落选者；供应商看不到竞争对手。内部角色是否再拆"业务员 / 采购"两条线，见下方确认清单第 ⑤ 条。

Open Questions

业务待确认清单

① Brief 承接与拆解实际 Brief 长什么样（正式文件还是微信几句话）？拆解谁在做、按什么习惯拆？有没有一个需求包拆给两家分单的情况？
② 匹配维度校准选供应商最看重的前三个因素？有没有一票否决项（指定认证、必须验厂）？客户提供的供应商是"必须优先"还是"仅供参考"？维度数据现在记在哪？
③ 内审与客户交互Demo 当前实现：定商由 Eastlink 内审确定，客户不再二次确认。待确认：内审谁来审——业务员还是主管？定商结果以什么形式同步客户（邮件/月报/系统通知）？
④ 设计与打样顺序Demo 当前实现：先设计定稿 → 候选供应商打样 → 比样后定商。待确认：打样候选名单是否需要客户确认（Demo 假设只内审）？打样费用谁承担？
⑤ 内部角色分工谁接 Brief、谁拆解、谁选供应商、谁对客户？要不要拆成业务员 / 采购两条线？一个业务员同时跟几个项目？
⑥ 现状痛点整个流程最耗时、最容易出错的是哪一步？现在靠什么在管（Excel/微信/邮件）？最想被系统替代的是哪部分？

Roadmap

分期规划

P1 · 本 Demo 范围三份主数据 + Brief 拆解 + 需求包匹配（多维度打分）+ 内审流（含定商）/ 设计稿客户确认 + 质量控制塔 + 角色权限。
P2 · 系统化协同真实后端与账号体系、客户在线门户、供应商门户（接任务/报价）、打样与订单跟进、绩效数据沉淀。
P3 · 智能化匹配模型基于历史成交自学习、AI 拆解 Brief、AI 推荐供应商与风险预警。
