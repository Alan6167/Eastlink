Overview

总览

Platform Thinking

Eastlink 是什么：客户给一个 Brief，平台把它变成一组"选对了的供应商"和"确认过的设计"

客户提交 Brief → 业务侧拆解成需求包 → 从供应商池按维度匹配 → 内审 → 客户确认 → 设计稿协同定稿。所有需要人做判断的动作统一进右侧审核中心；所有资源沉淀在客户、供应商、项目三份主数据里。

需求包状态机待匹配 → 内审中 → 待客户确认 → 已确认；内审可退回，客户可要求换选（记录原因后回到待匹配）。
为什么按需求包流转一个 Brief 往往多个品类，需要不同供应商分头满足；客户审的是"每个需求包的推荐名单"，不是抽象的整个项目。
设计稿挂在需求包下、带版本：内审 → 客户确认 → 定稿；修改意见记录原文，新版本重新走流程。

供应商池来源：客户提供 / 自主开发 · 六种准入状态

供应商池是一级资源库，为「匹配」供给候选；客户提供的供应商对该客户全量可见（含未准入），平台帮客户把他的供应商盘子管出质量。

Matching Model

匹配模型：先硬过滤，再 9 维度加权打分

维度默认权重数据来源计算口径
品类专精20主营 / 兼营品类主营 100，兼营 82
工艺覆盖15工艺能力标签需求工艺覆盖率 ×100
认证覆盖15资质证书需求认证覆盖率，缺项列入风险提示
质量表现12质量通过率直接取值
交付可靠10准时率 + 平均交期准时率 60% + 交期达标 40%
价格竞争力10报价竞争力指数直接取值
产能匹配8月产能 vs 需求量富余 1.5 倍满分，不足按比例扣
客户经验5服务过的客户服务过该客户 100 / 有出口经验 65 / 无 40
风险等级5风险评级低 100 / 中 60 / 高 25
硬性过滤准入状态必须"已准入 / 合作中"；品类必须覆盖。被排除者在漏斗里透明可见（谁、为什么）。
权重可调匹配工作台里拖滑杆实时重排——演示"匹配是按维度算出来的，权重变了排序就变"。默认权重待业务员校准。
输出总分 + 维度得分条 + 自动推荐理由 + 风险提示（缺认证 / 产能缺口 / 交期超限）。最终由人勾选，系统记录依据。

Roles

角色权限矩阵

业务员管理层客户供应商
总览全量 + 待办全量 + 风险仅自己项目与待确认仅自己的合作
项目管理可操作只读仅自己项目，只读不可见
匹配工作台核心操作不开放不可见不可见
供应商管理全池全池只读"我提供的"全量 + "合作中的"，无内部评分仅自己档案
客户管理可操作只读不可见不可见
审核中心内审动作查看批准 / 换选 / 设计定稿合作通知

原则：客户看不到供应商池全貌、内部打分与落选者；供应商看不到竞争对手。内部角色是否再拆"业务员 / 采购"两条线，见下方确认清单第 ⑤ 条。

To Confirm With Sales

待业务员确认清单（拿着本 Demo 对照访谈）

① Brief 承接与拆解实际 Brief 长什么样（正式文件还是微信几句话）？拆解谁在做、按什么习惯拆？有没有一个需求包拆给两家分单的情况？
② 匹配维度校准选供应商最看重的前三个因素？有没有一票否决项（指定认证、必须验厂）？客户提供的供应商是"必须优先"还是"仅供参考"？维度数据现在记在哪？
③ 内审与客户确认内审谁来审——业务员还是主管？客户实际怎么确认供应商（邮件/会议/全权委托）？换选一般给什么理由？
④ 设计稿协同设计稿谁出（自有设计/供应商/客户自带）？先定供应商再出稿，还是先出稿再定供应商？客户改稿一般几轮、意见从什么渠道回来？
⑤ 内部角色分工谁接 Brief、谁拆解、谁选供应商、谁对客户？要不要拆成业务员 / 采购两条线？一个业务员同时跟几个项目？
⑥ 现状痛点整个流程最耗时、最容易出错的是哪一步？现在靠什么在管（Excel/微信/邮件）？最想被系统替代的是哪部分？

Roadmap

分期规划

P1 · 本 Demo 范围三份主数据 + Brief 拆解 + 需求包匹配（多维度打分）+ 内审/客户确认流 + 设计稿协同 + 角色权限。
P2 · 系统化协同真实后端与账号体系、客户在线门户、供应商门户（接任务/报价）、打样与订单跟进、绩效数据沉淀。
P3 · 智能化匹配模型基于历史成交自学习、AI 拆解 Brief、AI 推荐供应商与风险预警。
